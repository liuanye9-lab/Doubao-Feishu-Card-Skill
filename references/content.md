# 卡片内容与文案规范

这份规则吸收了 `lark-card-studio-full.zip` 的内容层设计，并与本仓库的源锁定、真实交互和 Seedream 5.0 Pro 规则合并。它只回答“写什么、如何分组、什么可以行动”，不替代 Card 2.0 Schema 或视觉评审。

## 输入与事实源

- `source_text` 是唯一事实源。用途、接收对象和风格只影响信息层级、语气和交付计划，不得静默改变原文事实。
- 文档、表格、截图和网页内容必须先由调用方提取为可核验文字；无法读取的内容不补猜测。
- 不编造数字、日期、姓名、负责人、用户 ID、群 ID、链接、图片 key、审批号或线上结果。
- 没有真实值就省略对应字段或组件，不写 `TODO_*`、`—`、`N/A`、`mock_*` 或其它看起来像真实值的占位物。
- 示例/模拟数据只有在用户明确要求演示或模板时才可使用，并在第一屏标注“示例数据”或“模拟数据”。

## 内容模式

先判断内容是总结流还是设计流，再确定信息顺序：

| 模式 | 触发信号 | 默认结构 |
| --- | --- | --- |
| `meeting_summary` | 会议、纪要、群聊、多人讨论 | 讨论话题 → 确认事项 → 待办事项 |
| `work_report` | 周报、工作汇报、进展、已完成、风险 | 工作概述 → 已完成 → 进行中 → 下一步 → 风险/卡点 |
| `notice` | 通知、活动、培训、报名、日程 | 说明 → 时间安排 → 行动与安排 → 补充 |
| `long_summary` | 较长且无法可靠判定为以上模式 | 核心聚焦 → 详细信息 → 行动 |

分组只是布局建议。每一条都要保留来源行，不能为了填满模块而生成“暂无”“待确认”或新结论。

## 文字高亮块

高亮块是信息层级工具，不是装饰背景。Skill 的 `highlight` DSL 会编译为 Card 2.0 原生 `column_set`，在内部 `column` 上使用受限的 `background_style`，因此文字在 CardKit 中仍可编辑，也不会依赖 HTML/CSS。

优先高亮来源中已经明确的高显著信息：

| 信息信号 | 建议 tone | 典型位置 |
| --- | --- | --- |
| 核心价值、关键结论、结果 | `brand` / `success` | 标题之后、案例正文之前 |
| 注意、提醒、风险 | `warning` | 对应事实之前或紧邻事实 |
| 截止、必须、紧急 | `danger` | 首屏靠前，且保留完整原句 |
| 普通说明、背景长文 | 不使用高亮 | 卡片只留精简关键点，完整原文进入 `source.txt` 或真实来源链接 |

默认每张卡只选 1–3 个高亮块。高亮只能改变视觉承载，不得改写、压缩或丢失原文；长段落不塞进彩色面，按钮仍必须是独立的真实原生交互。

### 会议/沟通

- 讨论话题：围绕的核心议题、被反复讨论的主题；剔除寒暄和题外话。
- 确认事项：明确同意、已发生、已敲定的人选/时间/规则/方案。
- 待办事项：明确指派、计划、后续跟进、需要反馈或待解决的卡点。
- `@某人` 通常表示指派任务，但责任人仍以原文为准；没有明确责任人就不生成虚构人员组件。

### 工作汇报

- 工作概述放在首屏，用一句话概括已有成果或当前进展。
- 已完成必须写清“做了什么 + 产出/成果”；进行中保留原文进度或阶段；下一步必须带原文中的时间约束；风险写清问题与依赖。
- 原文没有数字时使用定性事实，如“完成初版”“通过评审”，不要为了做 KPI 卡补数字。

## 来源与链接

- 资讯、推荐、新闻和外部事实必须保留可验证来源；没有来源就只输出已验证内容，不伪造引用。
- 来源链接可内嵌在对应事实后，或在卡片末尾纵向列出；不要把多个链接挤在一行。
- URL 是被动来源还是明确行动目标要分开判断。只有“立即报名”“打开作品”“查看原文”等明确动作与真实 URL 成对时，才生成按钮。

## 按钮与真实交互

这是本仓库比源包更严格的安全边界：

- 不编造 URL，不使用占位 URL，不把本地路径、图片 URL 或示例地址当作动作目标。
- 原生 `button` 必须有一个可验证的真实行为：`open_url` 指向真实地址，或 `callback` / 表单提交连接到已实现的 application Bot 后端。
- 没有真实目标时不生成按钮；动作说明保留为原生文字，等待用户补充真实 URL 或后端能力。
- 需要表单的按钮必须绑定真实的 `form_submit` / `form_reset` 语义；没有回传处理服务时，不做视觉占位。
- `custom-bot` / webhook 只承载可跳转 URL，不宣称支持 callback、表单、卡片更新或图片切换。
- 交互放在 Card 原生 JSON 的 `button.behaviors`、表单或可验证的交互容器中；禁止旧 Card 1.0 的 `action` 容器。

## 图片与 CTA 分工

- AI 图片只由 豆包工作 Seedream 5.0 Pro 一次性生成完整信息型图片；不要用 HTML/CSS/SVG/Pillow 或第二个图片模型后处理。
- 图片可以表达主题、阶段、路径、输入→结果、指标关系或真实截图证据；原生 Card 只保留摘要、3–5 个关键点、来源图表和真实按钮，完整事实与长说明留在 `source.txt` 或真实来源链接。
- 图片中禁止按钮、CTA 胶囊、按钮形矩形、带动作标签的箭头、假链接和任何伪交互。视觉上像按钮的内容也算违规，不因“只是图片”而放宽。
- 真实截图、Logo、看板和照片按 `real_image` 保留来源与像素；不能让 AI 重绘准确 UI 或把截图里的按钮当成交互。

## 卡片摘要

每张准备发送的卡片都必须有 `config.summary.content`：

- 长度为 8–60 个字符，写“主对象 + 关键结论”；
- 摘要只能归纳卡片正文已有事实，不能引入正文没有的数字或结果；
- 不写“新消息”“卡片”“你有一条新通知”等平台默认文案，也不写占位文本。

## 内容层发送前检查

- [ ] 每个可见事实都能回溯到 `source_text` 或明确标注为示例数据。
- [ ] 摘要存在且是 8–60 字的真实结论。
- [ ] 可见文字只有摘要、3–5 个关键点、指标/图表和 CTA；单块不超过 220 字，全卡不超过 900 字。
- [ ] 默认约 3–6 个语义 Emoji，每个关键模块最多一个；显式 `off` 除外。
- [ ] 来源链接、行动 URL、人员和图片 key 都是真实值。
- [ ] 没有占位内容、假 URL、假 ID 或伪造指标。
- [ ] 真实按钮只出现在原生 Card，图片里没有按钮或伪按钮。
